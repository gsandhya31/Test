Automation Platform Roadmap · Future State · Operating model

What changes: from BU-specific automation to a shared utility platform

The platform changes how automation is built, controlled and owned — not just how much of it exists.
TodayAutomation built per BU, per use case
Future stateAutomation assembled from 9 shared utilities on ServiceNow
Build approach
Each use case starts from zero — bespoke macros, scripts and workflows per team
Domain teams assemble agents from a catalogue of proven utilities; new use case = configuration, not a build
Time to deploy
Months per use case; dependent on scarce technical capacity in each BU
Weeks — utilities are pre-built, pre-tested and pre-approved; only domain rules are new
Controls & governance
Controls re-designed and re-evidenced for every automation; inconsistent audit trail
Controls, logging and model governance inherited from the platform once; every agent is auditable by default
Ownership
Fragmented — owned by whoever built it; key-person risk when they move on
Utilities owned centrally by the platform team; domain logic owned by the business — clear split
Coverage
Pockets of automation in the highest-volume processes; long tail untouched
All 13 domains can draw on all 9 utilities — the long tail becomes economic to automate
Cost profile
Linear — every use case carries its full build and maintenance cost
Front-loaded then flat — utility cost is shared; marginal cost per use case falls with each reuse
Proven today3 utilities live on Settlements pre-matching — the operating model exists in miniature
PlatformServiceNow as the shared execution layer — existing estate, no new procurement
AskFund the remaining 6 utilities and the platform team; domains onboard against the catalogue

Automation Platform Roadmap · Future State · Maturity

From pilot to self-service: the platform maturity path

Each level changes who builds, how fast, and how much human oversight is needed. No dates — the path is defined by capability, not calendar.
We are here
Level 1
Pilot
We build for one domain to prove the pattern
Who builds
Platform team, hand-in-hand with Settlements
Scope
3 utilities · 1 domain · pre-matching alleges flow
Oversight
Human validates every output
Exit criterion: pilot metrics met; utilities stable in production
Next
Level 2
Reuse
We build once; adjacent domains adopt
Who builds
Platform team builds utilities; domain teams request onboarding
Scope
5–7 utilities · settlement-cycle and intake domains
Oversight
Human reviews exceptions; straight-through for matched items
Exit criterion: a second domain live without new utility code
Level 3
Self-serve
Domain teams configure agents themselves
Who builds
Business analysts in each domain, from the utility catalogue on ServiceNow
Scope
All 9 utilities · any of the 13 domains
Oversight
Platform-level controls and monitoring; humans handle escalations
Exit criterion: use case live end-to-end without platform-team code
Level 4
Autonomous ops
Agents run end-to-end with human governance
Who builds
Agents compose utilities dynamically within approved guardrails
Scope
Cross-domain workflows — e.g. trade to settlement to reconciliation as one agentic chain
Oversight
Humans set policy, review performance and intervene on breaches
Target state: operations capacity scales without headcount
Each level is earned by the one before — the pilot is Level 1 of a four-level path, not a one-off project.
